# Proposal: a trusted backend for the Consisto wallet and account deletion (not implemented)

> **Update (Phase 11C.2): the rules are now staged.** `firebase/firestore.rules` is **Part A only** (wallet integrity, the production deployment candidate). Part B (habit, completion and note validation) is `firebase/rules/part-b.rules` and the eventual end state is `firebase/rules/combined.rules`; all three are generated by `npm run build:rules`. Where this document says "the proposed rules" and describes habit, completion or note validation, that part is now **Part B**, and one wallet detail changed: a freeze purchase must cost exactly 20 coins. See `RULES_STAGED_STRATEGY.md`.

Status: **a proposal only.** No function was written or deployed, no Android change was made, and no rule was published. It exists so the decision can be made later with the facts in one place.

## Why and how much
Coins are purely virtual: no money, prizes, discounts or rankings with real-world consequences. So the goal is **integrity of a game mechanic and protection from accidental corruption**, not defence against a determined adversary. That makes a full server-authoritative wallet **optional**, and the proposal is staged so each stage is useful on its own and the expensive one can be skipped.

Today (see `WEB_SECURITY_AUDIT.md` and the rules tests in `tests/rules/`): the Firestore rules check that a wallet change matches a ledger entry in the same transaction, and the proposed rules in `firebase/firestore.rules` additionally check the entry's shape (type, id pattern, amount per type, price, freeze removal, month counter). What no rule can check is that a reward was **earned**, because that depends on many completion documents.

## Principles
1. **No change to the reward rules or amounts.** The server runs the same code as the Web: `domain/rewards.ts`, `ledger.ts`, `freeze.ts`, `streak.ts`, `schedule.ts` are pure TypeScript. Extract them into one shared package imported by both the Web and the functions, with the existing unit tests moved with them. A parity test feeds the same fixtures to the TypeScript code and to the Kotlin `RewardRules`/`WalletLedger` (the Kotlin side is read only here) to keep the two in agreement.
2. **Deterministic ids stay.** `daily_{date}`, `{id}_grantN`, `{id}_revN`, `milestone_{habit}_{n}_{start}`, `freeze_buy_{requestId}`, `freeze_apply_{habit}_{date}`, `welcome_freeze`. Idempotency, duplicate prevention and replays keep working, and existing ledgers need no migration.
3. **Clients never claim a reward.** They write completions (as now). The server decides what is earned.
4. **Android keeps working unchanged until it chooses to move.** The stage that breaks it is last and separate.

| 2 | **Reconcile and operations on the server for the Web:** `onCompletionWritten` (debounced reconcile from stored completions), callables `buyFreeze` and `applyFreeze`, `onUserCreated` (creates the profile and the welcome freeze), `deleteAccount`. Recommendation: do stages 0 and 1 for the Web-only launch. Do 2 to 4 only if coins ever gain value outside the app, or if Android is being reworked anyway.

## The functions (2nd generation, TypeScript, Firebase Admin SDK)
- **`onCompletionWritten`** (Firestore write of `habits/{id}/completions/{date}`): coalesce per user (a short delay, one run per user at a time), read the user's habits, completions, active rewards and freezes, call the shared `planRewards`, then apply grants and reversals as Firestore transactions with the deterministic ids. Pending adjustments use the same `grantReward`/`revokeReward`. A habit's `rewardsIgnoredThrough` is honoured only if the habit has `migratedFrom` and the date is not after the document's server update time (it is client written).
- **`buyFreeze(requestId)`** (callable): in one transaction check price, coins, hold limit (owned + used this month), monthly counter; write the entry `freeze_buy_{requestId}` and the wallet. The request id must be a UUID.
- **`applyFreeze(habitId, date)`** (callable): in one transaction check owned freezes, the 3-day recovery window and eligibility (`FreezeRules`), "already frozen", and the monthly counter; write the freeze, the counter, the entry and the wallet together.
- **`onUserCreated`** (Auth): create `users/{uid}` with 20 coins and the welcome freeze under `welcome_freeze`, replacing client profile creation (and the Web's guest-import profile creation).
- **`deleteAccount`** (callable, the user must have signed in within the last 5 minutes): the only code that sets the deletion marker and removes data. See below.
- **`auditLedger`** (detective, stage 1): described in the table.

Cross-cutting: `maxInstances` per function; a per-user operations counter inside the transactions (for example at most N wallet operations per minute); idempotency keys on every callable; structured logs and an alert on any compensating entry.

## Account deletion (stage 3 of the Phase 11B task)
The problem: the profile field `deletionRequested` is writable by its owner, and once it is true the rules let the owner delete the ledger collections and the profile (Android's own deletion flow relies on exactly this, and Android must keep working). Any script running as the user can therefore wipe the wallet history and reset the wallet; and an XSS could lock a victim's wallet for good.

What was done now, without breaking Android:
- The Web never writes the flag: no Web code path can (tests in `tests/accountSafety.test.ts` pin this: the ledger transaction, the habit writer and the import backend all refuse it, and a source scan fails if any new code mentions it outside the read side).
- The Web **reads** the flag: an account whose deletion has started takes no wallet change and no reward reconcile, and shows a clear message.
- The proposed rules still allow the owner to set the flag, because Android does. They remove the other ways to abuse the profile (unknown fields, a moving transaction pointer, extra profile fields on creation).

What cannot be done safely without a backend: stopping the owner from setting the flag. The safe design is `deleteAccount` above: a callable that requires a recent sign-in, writes the marker with the Admin SDK, deletes the data in batches (resumable, idempotent, profile last, exactly like `AccountRepository.kt`), and finally deletes the Auth user. Then the rules can stop letting clients set `deletionRequested` or delete the ledger. A rules-only alternative, requiring `request.auth.token.auth_time` to be recent when the flag is set, would need testing on a real device to confirm Android's re-authentication refreshes the token before it deletes; it is **not** in the proposed rules for that reason.

One observation about Android (read only, not changed): its deletion flow empties `walletTransactions`, `freezes`, `freezeMonths`, `rewards`, `todos` and the habits with their completions, but not `dayNotes`, so notes can remain after an account is deleted. A `deleteAccount` function should remove them too.

## End-state rules (stage 4), for reference
```
match /users/{uid} {
  allow read: if isOwner();
  allow update: if isOwner() && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['displayName','isDark','updatedAt']);
  match /walletTransactions/{id} { allow read: if isOwner(); allow write: if false; }
  match /rewards/{id}            { allow read: if isOwner(); allow write: if false; }
  match /freezes/{id}            { allow read: if isOwner(); allow write: if false; }
  match /freezeMonths/{id}       { allow read: if isOwner(); allow write: if false; }
  // habits, completions and notes stay owner-writable with the validation already in firebase/firestore.rules
}
```
Profile creation, the wallet fields, the welcome-freeze marker and the deletion marker are then written only by the functions.

## Cost and operations
- Cloud Functions require the **Blaze (pay as you go)** plan. At this scale the cost is small, but set a **budget alert** first. Roughly one function run per completion toggle (debounced) and one per freeze action.
- Use the **Firebase emulators** (Firestore, Functions, Auth) in CI. Rules and functions get tests with the same fixtures as the Web and Android write shapes.
- Deploy functions, rules and hosting separately, and always rules last. Keep a rollback (the previous rules file and function versions).

## Risks of the proposal itself
- **Time zones:** rewards depend on the user's local date. A server that guesses wrongly would reverse or withhold a reward. Mitigation: a validated client date within +/- 1 day of server time, or a stored time zone.
- **Two writers during stages 2 to 3:** Android and the server both write the ledger. The deterministic ids and transactions make this safe, but the auditor must treat an Android-written entry as valid.
- **Latency:** a server-granted reward appears after a short delay instead of instantly. The Web can show the coin immediately from the listener once the entry arrives.

## Decisions needed before starting
1. Do coins ever gain external value? If not, stop after stage 1.
2. Is the Blaze plan acceptable?
3. Time zone approach: callable argument or a profile field.
4. Whether Android's migration (stage 3) is planned, and when.
