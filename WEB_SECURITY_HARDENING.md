## Stage by stage

### Stage 1: project and environment protection (done)
- The repository exists (branch `main`, one commit, no remote). `.env.local` is ignored (`git check-ignore` confirms) and was **never committed** (`git log --all -- .env.local` is empty). Nothing sensitive is tracked. All real work is still untracked: review and commit it when you choose.
- `.gitignore` extended: every `.env*` except the new `.env.example`, crash dumps (`hs_err_pid*.log`, `replay_pid*.log`), `_tmp/`, `*.log`, Firebase local state.
- `.env.example` (names only, no values) documents every variable, says the six Firebase values are public identifiers and that no credential may ever be put in an `EXPO_PUBLIC_` variable, and sets `EXPO_PUBLIC_GUEST_IMPORT_ENABLED=false`.
- The production test knob `consisto_mock_start_coins` is now development-only (`__DEV__`); it is gone from the production bundle.
- No service account or private key exists anywhere in the web project (`verify:build` scans for them on every build).
- Development hooks (`__consistoFake*`, `consistoDev`) were already stripped from production builds; `verify:build` now fails the build if any returns.

### Stage 2: Firestore security (done as a proposal; not published)
`firebase/firestore.rules` tightens the rules in force. **Compatibility with Android is the design constraint**, so it was built from Android's actual write code (`WalletRepository.commit`, `HabitRepository`, `DayNotes`, `AccountRepository`, `GuestMigration`) and proven in the emulator: every Android-shaped write and every Web-shaped write (including the real `createCloudLedger`, `planImport`, `habitCreateFields`) succeeds under **both** rule sets, and Android's account deletion flow (flag, completions, habits, ledger collections, todos, profile) still runs end to end.

| Area | Rules in force | Proposed |
|---|---|---|
| Ledger entry | any `type`, any id, +/-20 | a known type with its id pattern and amounts: daily exactly 1, milestones 5/10/20, price 20 (earlier 10), freeze removal -1, welcome freeze once |
| Free freezes | a "purchase" for 0 coins, or an invented entry giving +1, is accepted | refused |
| Freeze applied with none owned | accepted (entry removes nothing) | refused (entry must remove one) |
| Monthly limit | skippable (counter not required) | the counter must go up by exactly one in the same commit |
| Pending adjustment | can be erased with an invented entry | refused |
| Pointer `lastTransactionId` | can move alone | only with its entry |
| Reward record | any amount or type | amount 1/5/10/20, a known type |
| Habits | any field, any size, any nested path | validated types and bounds, only `habits/{id}` and `completions/{date}` |
| Completions | any id or fields | id is a date, known fields only |
| `todos` (legacy) | open writes | read and delete only (Android still deletes them on account deletion) |
| Profile create / update | any extra fields | exactly Android's fields; updates only on known fields |
| Cross-user / signed-out access | denied | denied (tested on every collection, read, write, delete and list) |

The test file lists each audit finding as "old = allowed, new = refused", so the finding and its fix are both on record, and everything that must stay refused is refused by both.

What the proposed rules deliberately do **not** do, and why:
- They cannot prove a reward was **earned** (needs the server).
- They have **no date window for freezes**: Android's guest import replays old freeze dates through the same writes, so a window would break that Android feature (a test pins this).
- They do **not** stop the owner setting `deletionRequested` (see Stage 3).
- Hold limits and eligibility stay client side.

**Before anyone publishes them** (needs your approval):
1. These rules were checked against the **current** Android source only. I could not see older Android versions, which may write shapes the current code no longer does (a different ledger type, a profile field such as the legacy `freezeDates`). Check the Android release history or the real `walletTransactions` and profile documents of a few existing accounts for types and fields outside the lists in the rules. This is the main residual risk.
2. Smoke-test on a real Android build against the emulator or a test project: sign in, create, check, edit, reorder and delete a habit, a note, a reward and a reversal, buy and apply a freeze, and the account deletion flow.
3. Publish with `firebase deploy --only firestore:rules` (never a bare `firebase deploy`; `firebase.json` is hosting only so it cannot publish rules by accident), keep the previous rules file for an immediate rollback, and watch for permission-denied errors for a day.

### Stage 3: account deletion (done as far as is safe; a backend is required for the rest)
- The Web **never writes** `deletionRequested`/`deletionRequestedAt`: the ledger transaction, the habit writer and the import backend all refuse it, and `tests/accountSafety.test.ts` scans the source so a future change that mentions the flag outside the read side fails the tests.
- The Web now **reads** the flag: an account whose deletion has started (from Android) takes no wallet change and no reward reconcile, and shows "This account is being deleted, so the wallet can no longer be changed."
- Account data is preserved: nothing in the Web deletes or resets anything.
- The proposed rules still let the owner set the flag, because Android's deletion does exactly that from the client. Closing that hole **requires a backend** (`deleteAccount`, a callable that requires a recent sign-in), documented in `CLOUD_FUNCTIONS_PROPOSAL.md`. I did not invent a rules-only workaround: a recent-sign-in check in the rules (`auth_time`) would need a device test of Android's re-authentication first.
- Observation, read only: Android's deletion does not remove `dayNotes`.

### Stage 4: habit validation and limits (done)
- `domain/habitLimits.ts`: one set of bounds shared with the rules (name 1 to 1000 characters, goal and why up to 1000, weekly target 1 to 7, at most 7 rest days with real day names, valid dates, at most 20,000 completed dates, at most 2,000 schedule periods, field types, reminder `HH:mm`). They are generous on purpose: Android has **no length limit** when a habit is created, and an update validates the whole document, so tighter bounds would block ordinary check-ins on legacy habits. The limits users actually meet (100-character names, 300-character goals) are unchanged.
- The habit writer validates before sending (create and update). A bad habit is refused with a reason, the app undoes its local change and tells the user.
- A cap of 200 habits per account on the Web (Android has none, so an account can already hold more; the Web just refuses to add beyond it).
- Guest import: habits that are too large or invalid show why in the preview and cannot be ticked; at most 200 habits per import; checked again before any write.
- Tests: `tests/habitLimits.test.ts` (30 cases), `tests/accountSafety.test.ts` (6), `tests/appCheck.test.ts` (6), and the rules tests.

### Stage 5: hosting security (done)
- `firebase.json` (hosting only): single-page-app rewrite, `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, immutable caching for hashed assets and `no-cache` for `index.html`. `.firebaserc` names the project `habbit-tracker-12`.
- The CSP allows only this origin, `*.googleapis.com` (Authentication, Firestore, App Check), the reCAPTCHA hosts, `data:`/`blob:` images and fonts, and **no `unsafe-eval` and no inline scripts**. It does allow inline **styles** (React Native Web writes styles at runtime; unavoidable). It forbids framing, plugins and `<base>` injection. Testing it against the real build found one real gap (Firestore's connection test loads an image from `google.com/images/`), which is now allowed narrowly.
- `ErrorBoundary` in the root layout: a plain "Something went wrong" screen that never shows the error, its message or a stack.
- The Firebase Hosting emulator does **not** apply custom headers (confirmed with a minimal config), so `verify:csp` serves the real build with the headers and rewrites read from `firebase.json` and drives headless Chrome. It proves the policy values work with the app; that Firebase Hosting sends them is its documented behaviour. **After the first deploy, run `curl -I https://<your-domain>/` and confirm the headers.**
- `npm run verify:build` is the gate before any deploy.

### Stage 6: App Check (prepared, off)
- `services/appCheck.ts` starts App Check only when `EXPO_PUBLIC_APPCHECK_SITE_KEY` is set (it is not), with reCAPTCHA Enterprise by default (v3 supported), and a debug provider in development builds only. It never throws and is never enforcing. Setup, monitoring, rollback and the reason not to enforce are in `APPCHECK_SETUP.md`.
- **Enforcement stays off**: it is a whole-project switch, and the unchanged Android app has no App Check, so enforcing Firestore or Authentication would lock all Android users out.

### Stage 7: wallet review (done: documented; the client-trust limitation remains)
Client-side enforcement already in the Web (and tested in Phases 9D.5 and 10): idempotent ids for every operation; one wallet operation at a time; purchases need coins, respect the hold limit and the monthly limit read from the server's `freezeMonths` counter; applications use one owned freeze, respect the monthly counter and (client side) the 3-day recovery window and eligibility; balances never go below zero (a reversal beyond the balance becomes a pending adjustment); a missing profile creates nothing; cross-user isolation (listeners keyed and disposed per account); an account being deleted takes no wallet change. The proposed rules now enforce on the server the parts that rules can: entry shape, amounts, price, freeze removal and the month counter. The remaining limitation: **a determined signed-in user can still claim "+1 for a date they did not complete" and apply a freeze outside the 3-day window**, because earning and eligibility need server code. Given that coins have no external value this is a proportionate residual risk. The future architecture (a shared domain package, detective `auditLedger`, callables, `onUserCreated`, `deleteAccount`, the staged rollout, costs and the Android dependency) is in `CLOUD_FUNCTIONS_PROPOSAL.md`. Reward amounts and the existing wallet rules were not changed.

### Stage 8: guest migration (done)
`EXPO_PUBLIC_GUEST_IMPORT_ENABLED=false` for production: it is false in `.env.example`, the import is off in any build where the flag is not exactly `true`, and `verify:build` fails if the flag is `true` in any env file or in the build environment. Development builds keep it on for the tests.

## Remaining risks
1. **Wallet integrity is still client trusted** for earning and for the freeze window (Stage 7). Low impact given virtual coins.
2. **The proposed rules are unproven against older Android versions** and are not published.
3. **Owner-settable `deletionRequested`** remains until a backend exists (Stage 3).
4. **App Check cannot be enforced** while Android lacks it.
5. **Console settings are unverified** (API key restrictions, authorized domains, password policy); I have no Console access.
6. **Headers on the live host** must be confirmed after deploy (the emulator cannot show them).
7. **Habit and import limits** are client plus (once published) rules; old clients that bypass them are caught only by the rules.
8. All of this work is **uncommitted and untracked** in git.
