> **Update (Phase 11C.2): the rules are now staged.** `firebase/firestore.rules` is **Part A only** (wallet integrity, the production deployment candidate). ## Scope clarification (Phase 11C.1)

You confirmed that **no one runs an older Android version: only the current Kotlin source has to be supported.** So:
- The rules are **not** widened for obsolete versions. The proposed `firebase/firestore.rules` is unchanged by this clarification.
- The legacy `paidWith: "coins"` freeze format needs **no** backward compatibility in the rules. Existing freeze and ledger records are written once and never edited (their rules are create-only), so records of that format that may already exist stay valid and readable whatever the rules say; the only question is whether the **current app can write** one, and it cannot (`applyFreeze` writes `paidWith: "inventory"`, 0 coins, -1 freeze). The stricter rule is therefore safe on that point whatever the scanner finds. The scanner still reports `freezes.paidWith` so you know what is in the data.
- What still must be checked against **existing production data** (the clarification keeps this requirement) is the part of the rules that **re-validates stored documents when the current app updates them**: habits, completions and day notes (section 4.1). Historical records written by past app versions can still sit in those collections even if no old app is in use.
- Risks 1, 4 and 5 in section 7 and the "older versions" rows in section 5 are therefore **out of scope**; they stay in this document only as a record.

## 4. Existing data

### 4.1 Which documents the rules can actually break
A rule only judges a document when it is **written**. So:
- **Habits:** every check-in, edit and reorder updates the habit document, and the **whole resulting document** must pass `validHabit`. A legacy habit that breaks a bound would stop working in Android (the action fails). This is the main data risk.
- **Completions and notes:** Android merge-writes them; the resulting document must pass (unknown legacy fields would block it).
- **Profiles:** judged only on the keys that change, so extra legacy fields are harmless. Create rules apply only to **new** accounts, including those created by an old app version that is still installed.
- **Ledger entries, freezes, counters, reward records:** created whole and never edited, so existing ones are never re-checked. They matter only as evidence of what older versions **write**.

### 4.2 What the Kotlin readers tolerate (so what legacy data can exist)
Read from `HabitRecordParsing.kt`, `AppViewModel.habitFrom`, `WalletRepository.kt`, `WalletLedger.kt`: habits without `createdAt`, `sortOrder`, `goal`, `why`, `archived`, reminder fields or `scheduleHistory`; `createdDate` missing (reads as ""); `color` missing (green); numeric fields read through `as? Number`; `restDays` as a list; completions as `completed ?: false` plus the legacy `completedDates` array "for habits saved before completion documents existed"; reward records missing `type` (derived from the id); rewards granted "before reward records existed" (entry only, recognised by id); freezes with `paidWith` missing (defaults to `"coins"`); the profile's legacy `freezeDates` ("from before per-habit freezes; never written"); a profile `isDark` ("older installs kept the theme on the profile"); the `todos` collection ("from the removed Daily To-Do"); freeze purchases "earlier ones were -10".

All of these shapes **pass** the proposed rules in the emulator (`tests/rules/legacy.rules.ts`: 32 tests per rule set, 64 in all, including the RISK PROBES below), with one exception that is a question, not a failure: **a legacy freeze applied by paying coins** (probe in section 5).

### 4.3 The read-only scanner (the way to learn the real answer)
`scripts/audit-existing-data.mjs` evaluates the stored documents against the same conditions as the rules. Its checks live in `scripts/lib/rulesCompat.mjs` and are **tested against the real rules in the emulator**, so it predicts the rules exactly. It only reads (the unit test runs it against a fake that throws on any write). It prints **counts, field names and maximum lengths only**: never a name, email, note text, value, uid or path (a short hash labels a problem document; `--show-paths` is opt-in for a private terminal).
```
npm install --no-save firebase-admin          # not added to package.json
gcloud auth application-default login         # your own identity; no key file
node scripts/audit-existing-data.mjs --project habbit-tracker-12 --yes --out audit-report.json
```
Reads are billed per document (default at most 5,000 per collection group; `--all` reads everything). The report ends with a `verdict` block; the gates G1 and G2 are read from it. I did not run it: it needs your credentials, and the audit rules forbid touching production.

## 8. Publication recommendation, in detail

1. **Now:** do not publish.
2. **Gather evidence (about an hour of work):** run the scanner (G1, G2), run the staging smoke test (G3), look at the Play Console version distribution.
3. **Decide by the evidence:**
   - All gates clean: publish `firebase/firestore.rules` with `firebase deploy --only firestore:rules` (never a bare `firebase deploy`; `firebase.json` is hosting-only so this command needs `--config` or a change you make deliberately), at a quiet time, and watch Console > Firestore > **Rules monitoring** for denied requests for 24 hours. Roll back with one click if they rise.
   - A shape is refused: widen that rule (for example accept `freeze_application` with coins when an older version needs it), add the shape to `tests/rules/legacy.rules.ts` as an accepted case, rerun the emulator tests, and repeat.
   - Still uncertain about old versions: **split the publication.** The wallet-integrity rules (items 3 to 6 of section 1) fix the real weakness. The habit validation (items 7 to 9) fixes only cost and abuse, and is the part with the most legacy-data exposure. Publishing the wallet rules first and the habit validation later (after the scanner is clean) halves the risk. I can prepare the two files and their tests if you want.
4. Whatever you publish, keep `android/firestore.rules` as the rollback copy.
